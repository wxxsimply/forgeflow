# 离线补丁审查：先看改动，再批准测试

本工具用于阶段 D 的准备工作，不会调用 DeepSeek、读取 API Key 或更新网站。它不是完整的 Agent 执行入口。PR #59 已合并；本轮新增本地审批/执行收据，执行命令现在必须带已有的 `--evidence-db`。

## 1. 提案是什么

提案是 UTF-8 JSON，不是 shell 脚本，也不是直接执行的 Git patch。它只包含以下五个字段：

- `schemaVersion`：固定为 `forgeflow.demo.patch/v1`。
- `taskId`：由操作者为任务指定的 32 位小写十六进制编号。
- `taskSha256`：已审阅任务正文的原始字节 SHA-256；换行变化也会改变摘要。
- `baseSnapshotSha256`：原始四文件经预检返回的 `snapshotSha256`。
- `files`：以 `greeting.go`、`greeting_test.go` 为键，以修改后的完整文件文本为值；至少有一个实际改动。

任务编号和正文摘要还必须通过命令行独立传入并匹配，不接受模型在 JSON 中自行加一个“已批准”字段。工具不读取任务正文，也不验证身份；操作者必须自己核对编号与正文的对应关系。

提案原始 JSON 最多 1 MiB（留出 JSON 转义空间），修改后的完整四文件快照最多 128 KiB。禁止修改 `go.mod`、`README.md`，禁止新增文件、目录、链接、删除或重命名。源码只接受 UTF-8 文本。

## 2. 先只读审查

在项目根目录运行下面的命令；尖括号内容需要替换，不要原样执行：

```powershell
python -B scripts/preview_demo_patch.py --proposal "<受控目录中的proposal.json>" --task-id "<32位任务编号>" --task-sha256 "<64位任务摘要>"
```

默认来源为公开的 `examples/preview-demo` 四文件模板。自定义 `--source` 也必须是受控的平铺四文件目录，不能包含 `.git`，不要指向完整 ForgeFlow 仓库或线上仓库。

输出中的 `diff` 用来逐行检查变动，`approvalSha256` 是本次批准所对应的内容摘要。JSON 会转义终端控制字符，避免模型代码直接发出终端控制指令。只读成功的 `checksPassed:true` 不表示代码编译或测试通过。

提案和差异可能包含源码。保存在私有、受控目录，不上传公共 PR 或普通日志；这里的白名单不是秘密扫描器。不要把私有代码或密钥放入这四个模板文件。目录不能由不可信用户并发修改，路径检查不是完整的恶意文件系统隔离。

## 3. 保存审查记录，再人工批准测试

先在自己控制的私有目录保存一份新收据。建议使用仓库已忽略的 `.forgeflow` 下的专用任务目录，先人工配置好目录权限；目录不能位于四文件源码内，工具不会自动创建父目录。Windows 需要合适的 ACL，POSIX 创建文件权限为 `0600`。不要提交 SQLite 文件及其 journal，也不要复制收据作为备份恢复额度。

```powershell
python -B scripts/preview_demo_patch.py --proposal "<同一提案文件>" --task-id "<同一任务编号>" --task-sha256 "<同一任务摘要>" --record-review "<私有目录中的review.sqlite>"
```

这个显式操作保存任务和原始/候选快照摘要，状态为 `reviewed`，还没有批准执行。文件已存在时拒绝覆盖；初始化失败会保留文件供核查，不能自动重建。收据不保存源码、Diff、任务正文、模型原始回复或测试日志，因此不是完整的原始证据归档。

读完差异，确认仅包含预期逻辑与测试，没有危险代码、删掉断言或伪造测试，再手动执行：

```powershell
python -B scripts/preview_demo_patch.py --proposal "<同一提案文件>" --task-id "<同一任务编号>" --task-sha256 "<同一任务摘要>" --sandbox --approve-sha256 "<刚才审阅的approvalSha256>" --evidence-db "<已有review.sqlite>"
```

不要编写“自动提取摘要再批准”的脚本代替人工审查。摘要绑定整个原始快照、候选快照与任务身份；其中任何内容变化都需要重新审查。

默认使用本地已缓存、事先信任的 `golang:1.22-alpine`，不会拉取镜像。沙箱沿用预检工具的固定测试命令、无网络、非 root、只读挂载、资源限制、总时限和按归属清理。默认 90 秒，`--timeout-seconds` 范围 1～120 秒，另预留清理时间。原始目录不写入，候选只在内存及一次性副本中使用，不执行宿主机命令。

容器隔离不是绝对安全保证，Docker daemon 和镜像必须受信任。批准的是代码内容，不是任意镜像；不要把不可信镜像传给 `--image`。密钥、其他项目和 Docker socket 不挂载进测试容器。

输出含 `sandboxAttempted`（已进入沙箱调用）和 `sandboxExecuted`（沙箱返回测试结果）；超时/清理异常不能算通过。`cleanup_unconfirmed` 时只核查输出的本次容器，不运行全局容器清理。测试退出零也不证明新需求已经实现，需要独立验收；模型可以修改测试，不能只相信模型自带的断言。

执行前先把批准和 `running` 状态提交到 SQLite，写入失败就不启动沙箱。沙箱返回后保存 `completed`、退出码、OOM 状态、实际镜像 ID 和本地时间戳；`completed` 仅表示测试结果已记录，`passed:false` 仍为失败。异常或中断保存 `unknown`，强制结束进程或结果保存失败可能留下 `running`。两种情况都阻止自动重复执行；没有退款、重置、补写成功或自动重试接口。

同一收据只能消费一次，成功和失败均不能再次用它执行。使用两个独立数据库连接同时批准，也只能有一个成功。默认审查命令加 `--evidence-db` 可以只读核对记录；如果源码或提案已变化，绑定检查会拒绝打开，保留原收据和对应输入供人工核查，不新建收据来掩盖失败。查看状态的 `checksPassed:true` 表示审查与读取有效，不表示历史测试成功，应查看 `evidence.state` 和 `evidence.result.passed`。

如果沙箱执行完但结果写入失败，报告会标明 `sandboxExecuted:true`、`checksPassed:false`，不能把它计为已保存的成功证据。异常原始文本不会写入收据。清理错误仍按沙箱报告中的容器名人工核查。

## 4. 本轮验证和剩余边界

快速检查命令：

```powershell
python -B -m unittest discover -s scripts -p 'test_preview_demo_*.py' -v
```

上一轮共运行 56 项离线测试，55 项通过、1 项因 Windows 未授予符号链接创建权限而跳过，耗时约 1.51 秒。本轮增加持久化收据测试，结果见阶段 D 准备记录。测试提案仅为注释改动，沙箱为 Fake，不是模型生成结果，不运行候选代码。本轮不改模板、不产生模型费用、不更新服务器。真实 Docker 候选集成测试仍待后续执行。

批准摘要不是签名，不防本地用户伪造；SQLite 也不是防篡改审计系统。本轮一次性消费只在同一份收据内生效，复制数据库、回滚文件或更换目录新建收据仍不受跨库约束，禁止用这些方式续跑。尚未保存完整执行证据或把预算账本接到请求上。后续需把授权、唯一任务目录、账本、提案和测试证据统一绑定，再单独确认真实付费调用范围。不能因此将阶段 D 或网页真实执行标记完成。
